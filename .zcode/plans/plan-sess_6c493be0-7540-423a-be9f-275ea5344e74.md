# SQLite Database Service — Railway Template

## Product decision (Step 1, written down first)

**Choice: (a) sqlite-web manager** — pinned `sqlite-web 0.8.1` on a maintained Python base, over a Railway volume.

- **Incumbent audit** (`railwayapp-templates/sqlite`, template `jOiNFt`, 865 deploys @ 71% health): ships `python:3.7-alpine3.17` (both EOL since 2023), unpinned `pip install gevent sqlite_web`, a custom gevent `wsgi.py` wrapper, a hardcoded `/data/database.db` seeded with Thomas-the-Tank-Engine sample data, and a `SQLITE_WEB_UI_PASSWORD` variable. The degradation band (29% of arrivals failing) is consistent with the rotted base image / unpinned deps.
- **(b) Datasette** rejected: it's a read-first *exploration/publishing* product (write via plugins), not a *manager*. Different product than what 865 projects are deploying.
- **(c) libSQL** rejected as a competitor: it already has a healthy Railway template (27 deploys @ 95%). It will be **documented in the listing as the networked alternative** for multi-service access — it's the honest answer to the wire-protocol limitation.

## Step 2 — Scaffold repo `sqlite3-railway-template` (in `C:\Users\HomePC\Documents\code\sqlite3`, published via `github-repo-setup` skill — GCM credential if `gh` unavailable)

Files:
1. **`Dockerfile`** (repo root — Railpack only auto-detects root): `FROM python:3.12-slim-bookworm`, `pip install sqlite-web==0.8.1 gevent==<pinned>` (no bind mounts — Metal builder rejects them), copy `entrypoint.sh`, `ENTRYPOINT`.
2. **`entrypoint.sh`**:
   - Fail closed if `SQLITE_WEB_PASSWORD` is unset (never credential-less).
   - Ensure `/data` exists; if no `*.db` present, create an empty default `sqlite.db` (no toy seed data — clean product).
   - Launch `sqlite_web` CLI: all `/data/*.db` files as args (multi-DB support), `-H 0.0.0.0 -p ${PORT:-8080} -x`, plus upload/creation flags (`--enable-load --upload-dir /data`; exact filesystem/create flags verified against `sqlite_web --help` inside the container during debug). Password comes from `SQLITE_WEB_PASSWORD`, which sqlite-web reads natively.
   - Serving: start with the plain CLI (supported path); if deploy debugging shows werkzeug flakiness under healthcheck, fall back to the incumbent's gevent-wrapper pattern, modernized. Decision recorded in the repo README.
3. **`railway.json`**: `DOCKERFILE` builder, `healthcheckPath: "/"` (login page, no redirect trap), `healthcheckTimeout: 300`, `restartPolicyType: ON_FAILURE`. Critical behavior also baked into the Dockerfile CMD per the skill's Metal/Railpack caveat.
4. **`README.md`**: deploy button, creating/opening DB files (UI create + upload), backup story (UI CSV/JSON export + Railway volume backups), and the two honest limitations: **no cross-service volume mounts** (with libSQL linked as the networked alternative) and **single-writer/concurrency caveat**.
5. **`TEMPLATE_OVERVIEW.md`**: listing per `railway-template-listing` skill — positioning ("SQLite on persistent storage with a web manager — for apps that don't need Postgres"), manager-vs-libSQL explainer, cost (~$5/mo + volume storage), troubleshooting (volume attach, password variable, concurrent writes), with the five exact required headings (`# Deploy and Host`, `## About Hosting`, `## Why Deploy`, `## Common Use Cases`, `## Dependencies for` + `### Deployment Dependencies`) at the end, raw markdown.

## Step 3 — Deploy and debug (`railway-deploy` skill)

`railway init` (resolve workspace via `whoami --json`) → `railway up` → set `SQLITE_WEB_PASSWORD=${{secret(24)}}` (quoted, expression survives as template default → zero-prompt deploys) → attach volume at `/data` → `railway domain`. Verify the full loop:
1. UI loads at the domain, login page 200 (healthcheck green).
2. Login with the generated password (read via `railway variables --service ... --json`), create a DB → create a table → insert rows → query them (browser UI).
3. Restart the service → query again → rows intact (volume proof).
4. Debug loop with `railway logs -b/-d` as needed; pin every dependency version before moving on.

## Step 4 — Publish and verify (`railway-template-publish` skill)

2. `railway templates create --json` → audit `serializedConfig` via `railway api`: repo source present, volume captured, **every variable carries a `defaultValue`** (password = `${{secret(...)}}` expression, no literal secrets captured).
3. `railway templates publish <draft-id> --category Storage --description "<≤75 chars>" --readme-file TEMPLATE_OVERVIEW.md --json`; swap repo README button to `https://railway.com/deploy/<code>`; re-run publish after any overview edit.
