# SQLite3 on Railway — SQLite with a web manager

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.app/new?github_url=https://github.com/lNamelessl/sqlite3-railway-template)

This template deploys [SQLite](https://sqlite.org) on a persistent Railway volume with
[sqlite-web](https://github.com/coleifer/sqlite-web) as a browser-based manager UI: browse
tables, edit rows, run queries, import/export CSV and JSON — no CLI required.

**What it is:** a single-service SQLite database you administer through a web UI.
**What it is not:** a networked database server. Other Railway services cannot connect to
it over the wire — see [Limitations](#limitations) for why, and when to use
[libSQL](https://github.com/tursodatabase/libsql) instead.

## What gets deployed

- **`sqlite3` service** — a pinned image (`python:3.12-slim-bookworm`, `sqlite-web 0.8.1`,
  `gevent 26.8.0`) serving the manager UI on Railway's public port.
- **Volume mounted at `/data`** — every `*.db` / `*.sqlite` / `*.sqlite3` file here is
  opened as a dataset in the UI. Your data lives here, across redeploys and restarts.
- **`SQLITE_WEB_PASSWORD`** — auto-generated at deploy time (`${{secret(24)}}`); find it in
  your service's **Variables** tab. The service refuses to start without it.

## Working with databases

- **Open:** all database files on the volume appear in the UI's dataset selector at the top.
- **Create:** set the `SQLITE_DATABASES` variable to a comma-separated list of names
  (e.g. `app.db,analytics.db`) and redeploy — the entrypoint creates any that don't exist.
- **Import:** the UI's *Load database* page uploads an existing `.sqlite` file onto the
  volume (uploads land in `/data`).
- **Query/edit:** each dataset supports the table grid editor, ad-hoc SQL queries, and
  structure changes; CSV/JSON import and export are built in.

## Backups

Two layers, both yours:

1. **Point-in-time download** — in the UI, *Export* any table as CSV or JSON, or download
   the whole database file (each dataset page has a download link for the `.db` file).
2. **Volume backups** — enable Railway's volume backups (or take a manual volume snapshot)
   in the service's volume settings. Backups capture the whole `/data` directory.

Schedule discipline is on you: SQLite won't remind you. For anything that would hurt to
lose, turn on volume backups the day you deploy.

## Limitations (read this before building on it)

- **Single writer.** SQLite allows one writer at a time; concurrent writes from multiple
  processes/instances will hit `database is locked` under load. This is inherent to SQLite,
  not this template. It is ideal for a single app instance, local-ish tooling, config/small
  datasets, and prototyping.
- **No cross-service mounts.** Railway volumes attach to exactly one service. Your API
  service cannot mount this volume, and nothing can talk to this database over a network
  protocol — SQLite is a file format, not a wire protocol. That's the honest limitation of
  SQLite-on-PaaS, and exactly why networked SQLite forks exist: if you need other services
  to connect to your database, deploy the **libSQL Server** template instead
  ([railway.com/deploy/…](https://railway.com/templates) — search "libSQL"), which speaks
  the Postgres-compatible libSQL/HTTP protocol.
- **One manager instance.** Scale this service to a single instance; the UI and the volume
  are not designed for horizontal scaling.

## Configuration

| Variable | Required | Purpose |
|---|---|---|
| `SQLITE_WEB_PASSWORD` | yes | Manager UI login password (auto-generated by the template) |
| `SQLITE_DATABASES` | no | Comma-separated list of database files to create at boot if missing |
| `DATA_DIR` | no | Data directory on the volume (default `/data`) |
| `PORT` | auto | Provided by Railway; the UI binds to it |

## Local development

```bash
docker build -t sqlite3-railway .
docker run --rm -p 8080:8080 -e SQLITE_WEB_PASSWORD=devpass -e PORT=8080 \
  -v "$PWD/data:/data" sqlite3-railway
```
